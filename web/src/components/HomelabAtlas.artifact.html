Notes

  • I use the laptop as the main control point. In a browser I open the home dashboard, this atlas, Grafana, the investment dashboard, and the other web apps through authenticated overlay access. The phone uses the same private access path for dashboards and also sends photos, wearable exports, and synchronized files.
  • The homelab host runs two kinds of work. Docker Compose runs the web applications and their databases. System services run jobs that need host files, timers, or tighter operating-system controls, including the agent gateway, investment pipeline, and health-data importers.
  • Syncthing connects the laptop, phone, and server. I use it to keep the Obsidian workspace, music, selected files, and incoming wearable exports available where they are needed. Application databases and generated files stay on the server unless a diagram explicitly shows them being synchronized.
  • External traffic has a specific purpose. WARP and ProtonVPN provide egress for selected download or lookup workflows. Model providers answer agent requests. Telegram carries bot conversations, digests, and failure alerts. AWS is used only when I start a CKA practice session.
  • This first diagram is the map for the rest of the site. Access and networking are expanded in 01 and 02. Applications are covered in 03 through 07. Agent, job-search, training, automation, investment, and health workflows follow after that.

Notes

  • The laptop and phone join the authenticated overlay as clients. I do not need to expose each dashboard to the public internet. Once a device is authenticated, it can reach the host and the application routes intended for that device.
  • Containers are split by workload. Most applications share the main application network so related services can call each other by container name. The fitness stack has its own network. Syncthing and the remote-desktop relay use the host network because their protocols need direct host connectivity.
  • qBittorrent deliberately shares Gluetun’s network namespace. It has no independent route to the internet. If Gluetun stops, download traffic stops with it. The books proxy is separate because only the book lookup workflow should use that ProtonVPN route.
  • Some small APIs run as host services instead of containers. The authenticated proxy forwards requests to them without making those APIs general public endpoints. This is how the CloudOps chat API, MCP gateway, investment dashboard, and health receiver fit beside Docker services.
  • I use the topology view when a dashboard opens but its backend does not respond. It shows whether to check device access, the host route, a Docker network, a shared network namespace, or a host-side service.

Notes

  • The phone collects wearable records through Gadgetbridge and Health Connect. Gadgetbridge is the main source for steps and heart rate. Its database export moves to the server through a send-only phone folder and a receive-only server folder.
  • A path unit notices a new Gadgetbridge export, and a timer provides a fallback check. The promoter waits for the file to stop changing, checks its schema and SQLite integrity, records the source hash, and atomically publishes a current snapshot. A bad or incomplete export never replaces the last good copy.
  • Health Connect uses a second route. The phone exporter sends authenticated requests through the overlay to the receiver. The receiver deduplicates logical records, keeps each unique raw payload in the source database, checks the generated snapshot, and replaces it atomically.
  • A daily timer makes a transaction-consistent backup of the Health Connect source database. This protects the write-side record independently from the read-only snapshot used by dashboards.
  • Grafana reads both verified snapshots without write access. The source policy prefers Gadgetbridge where the two feeds overlap and uses Health Connect only for supplementary records. I open /health from the laptop or phone to view the dashboards.

Notes

  • These sequences are the procedures I follow when normal architecture is not enough. The boot runbook shows which service managers start each part and where to check when the dashboard is unavailable after a restart.
  • The deployment runbook keeps code changes, validation, human approval, service restart, and post-deploy health checks in order. An agent may prepare and validate a change, but I explicitly approve any restart and keep control of merge and deployment.
  • The memory-pressure runbook checks the largest process first, lowers priority where possible, and asks before stopping work. The sync-conflict runbook stops automated edits and preserves both copies for human review.
  • The CLI update runbook covers mise-managed tools, the separate Hermes update, service verification, and Telegram failure reporting. The agent-incident runbook distinguishes provider trouble from an MCP guard refusal, so a failed model route is not mistaken for permission to bypass a data guard.
  • I keep the notes under each sequence because the diagram gives the order while the notes explain the decision points and expected result.
