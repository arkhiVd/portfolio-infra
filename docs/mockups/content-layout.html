One site, two CDNs, and stale pages

September 2026

Terraform deploys this static Astro site to a private S3 bucket. CloudFront reads it through origin access control. The browser calls a separate Lambda Function URL injected by Terraform for the visitor counter. That makes CloudFront the delivery cache for www.

What went wrong

Cloudflare also sat in front of the hostname. A new build could reach S3 and CloudFront while an earlier response still came from the other cache. Invalidating one layer did not prove that a visitor would see the new page.

The boundary

The apex keeps its Cloudflare redirect rule. The www record stays DNS-only, so CloudFront is the only cache that serves the site. The rule is simple enough to explain during an incident and avoids a second invalidation step.

What I check now

After a deployment, I use a cache-busting query string and inspect response headers. The expected server is AmazonS3 behind CloudFront, not a cached response from an extra proxy.

What it is for

The homelab gives me a smaller environment for Linux, containers, networking and recovery work. The useful part is not a rack photo. It is being able to trace a service boundary, write down a change and recover when an assumption fails.

AI workflow

I use AI to explore options, draft bounded changes and challenge assumptions. It does not get merge authority. I read the diff, run the relevant checks and keep claims tied to public evidence.

Setup and tools

Terraform describes infrastructure. GitHub Actions uses OIDC roles instead of stored AWS credentials. Astro produces static output. Local linting and builds catch the ordinary mistakes before review.

Reusable skills

Small written procedures keep repeated work consistent: inspect the current state, change one concern, validate it, then leave a short record of what changed. A skill is useful when another person can review the steps without sharing my machine.
