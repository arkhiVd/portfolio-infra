case study · serverless · 2026

ClearSky — multi-account AWS posture & cost platform

Answer two questions for any AWS account, continuously: what is running, and is it safe? Serverless end to end, stands up or tears down in one pipeline run.

problem

Posture tools tell you what is wrong, then ask you to trust them

Security scanners are usually opaque: a score appears, and the reasoning behind it is someone else's. I wanted findings that were reproducible — the same account state producing the same findings every time — with the AI layer strictly additive, able to explain and investigate but never to decide what counts as a finding.

The second constraint was money. This runs in a personal AWS account, so nothing may idle: no always-on compute, no NAT gateway, no managed scanner service.

architecture

Serverless, and read-only by construction

24+ detectors are pure functions — API responses in, findings out — so they are fixture-tested rather than mocked against live AWS. The entire backend runs on Python stdlib plus boto3: no layers, no third-party packages, nothing to patch. JWT verification, including RS256, is implemented in-process.

decisions and tradeoffs

What I chose, and what it cost

Lambda function URLs over API Gateway
Removes a service and its bill; CORS and SigV4 are handled at the function URL. Tradeoff: no usage plans or request validation, so validation lives in code.
Detectors as pure functions
Deterministic and fixture-testable, which is what makes findings trustworthy. Tradeoff: every new AWS API shape needs a fixture before it needs a detector.
Read-only IAM as the AI's hard boundary
The agent's tool loop is allowlisted to describe/list/get. It physically cannot mutate the account, so a prompt injection cannot become an incident.
Zero-dependency backend
No supply chain to audit and no layer builds in CI. Tradeoff: more code written by hand, including RS256 verification.

what broke

Recreating the repo silently broke every CI role

The repository had to be deleted and recreated. Every GitHub Actions job then failed to assume its role — with no code change and no policy change. The trust policies still matched what the documentation described.

CloudTrail's AssumeRoleWithWebIdentity events had the answer: the OIDC subject GitHub now presents is repo:owner@id/repo@id:context, and the immutable numeric ids in it change when a repository is recreated. Every trust policy pinned to the old subject stopped matching. The fix was to re-derive the subject from the actual token claim rather than from documentation, and to diagnose from CloudTrail's principalId instead of guessing at the policy.

The lesson generalises: an OIDC trust policy is a string comparison against a claim whose format the provider owns. Recreating a repository is not a no-op.
